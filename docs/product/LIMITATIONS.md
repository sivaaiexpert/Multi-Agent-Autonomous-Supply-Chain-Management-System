# Limitations

Read this before relying on any number or capability described elsewhere.

## Evidence

- **No customer has used this.** There is no customer data, no pilot result, no reference deployment. Every business result is on **synthetic** data (`SYNTHETIC` provenance) generated by `enterprise/profiles.py`.
- **Benchmark results are mixed and simulated.** The pre-registered 20-unit experiment found the lean AI policy ahead of the manual policy on mean simulated gross profit (CI above zero; better in 14/20 units) and on stock-out days (20/20), while the default service-first AI policy was *behind* the manual policy on gross profit (CI below zero; better in 7/20 units). Supplier outcomes are drawn from generated delivery histories; budget constraints are not simulated; demand shocks outside the generated history are not modelled.
- **The AI is not shown to be the cause.** The arms differ in policy (forecast + optimiser + rules), not only in the use of a language model. The language model writes advisory text; every number comes from deterministic code. The benchmark does not measure the model's contribution.
- **Savings are conditional.** "Savings" versus a lowest-price buyer can be negative on sticker price (the optimiser buys what is needed from suppliers that can deliver). ROI uses a realisation factor of 0.5 (a judgement) and, by design, no price for the platform: the user supplies the cost side.
- **Manual-effort figures are assumptions** (12 minutes per order line vs 5 per reviewed batch), not measurements.
- **Forecast accuracy** is back-tested on generated demand; it says little about real demand.

## Integration

- **No real ERP connector exists.** `MockERPAdapter` is in-repo; `RestERPAdapter` is a generic JSON contract tested only against the bundled mock server. SAP, Oracle, Dynamics and NetSuite are ADAPTER-READY (an interface to implement), nothing more. Real ERP projects involve authentication schemes, data models, custom fields, master-data mapping and change management this repository does not address.
- Inbound webhooks and outbound events were validated with local receivers, not with a customer's infrastructure. Outbound delivery is at-least-once; receivers must de-duplicate.
- Row-level rollback of a committed import is not implemented (restore from backup).

## Scale and architecture

- **Single node.** One SQLite database per tenant plus a control-plane database. No horizontal scaling, no managed database, no multi-region. The workflow engine keeps per-process state, so `make production` runs one worker.
- **Measured throughput is low and bounded**: about 1.6 completed workflows per second on one developer machine, with latency growing linearly under concurrency (10 -> 100 simultaneous lifecycles: P95 13 s -> 62 s). 0 errors in that test; no claim beyond it. The worker pool is small and fixed, and SQLite serialises writers.
- Database-per-tenant isolation is strong but does not scale to very large tenant counts without operational tooling that does not exist here (migrations across many tenants, fleet backups).
- Load tests use a deterministic decision path; LLM-enabled latency and cost under load were not measured.

## Security and compliance

- Controls are described in [SECURITY.md](SECURITY.md) with the tests behind them. There has been **no external penetration test, audit or certification**; the privacy features are technical controls that support compliance requirements, not compliance.
- The application serves HTTP only (TLS must be terminated in front). SQLite files are not encrypted at rest. The platform secret key has no rotation tooling. No automated dependency vulnerability scanning. The Streamlit console is not a per-user authenticated application (identity comes from configuration).
- Docker files and `make production` are not a validated production deployment (no HA, supervision, TLS, secrets manager, log shipping).

## Operations

- RTO was measured on a small synthetic tenant only; RPO is whatever backup interval is scheduled and no scheduler ships. No on-call, alerting or SLO tooling.
- Plans (pilot / professional / enterprise) are quota concepts. There is no billing, invoicing, payment or pricing logic; quotas are advisory unless enforced by configuration.
- Support, SLA, data-residency and contractual commitments are outside the codebase.

## Product scope

Single-echelon replenishment per tenant: no multi-warehouse transfers, no network optimisation, no production planning, no returns, no cost-to-serve model, no currency conversion within a tenant, no supplier negotiation. Demand forecasting uses classical statistical methods on daily history; new SKUs without history fall back to static reorder rules (flagged `basis = static_rule`).
