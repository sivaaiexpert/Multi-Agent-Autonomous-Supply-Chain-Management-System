# Evaluation methodology

Results live in `docs/EVALUATION_REPORT.md` (regenerated by `make eval`). This page explains what is measured and what is **not**.

## Layers
| Layer | Tool | What it proves |
|---|---|---|
| Unit / property | `pytest tests/test_forecast.py test_risk.py test_optimizer.py ...` | maths and constraints (incl. brute-force optimum check, 300 randomised plans) |
| Workflow | `tests/test_workflow.py` | agents, gate, faults, crashes, audit, idempotency on throwaway DBs |
| Scenario benchmark | `python -m evaluation.runner benchmark` | 114 deterministic scenarios + universal invariants |
| Chaos | `python -m evaluation.runner chaos` (`make chaos-test`) | scenario / expected / actual / pass / recovery time for the fault-injection subset |
| Studies | same runner | forecast accuracy, stock-out prediction, inventory simulation, optimiser vs baselines (all synthetic) |
| Live LLM sample | `--live-llm N` | real `llama3.2`: validity, groundedness, hallucination, instruction following, consistency, latency |

## Scenario design
Each scenario = DB setup + run config (scripted LLM reply / injected fault / node crash / patched tool) + simulated reviewer decision + **explicit expected outcome** (allowed final statuses, must/must-not reach the gate, extra checks). After every scenario the runner asserts: no dangling pending orders, no order `SENT` without a human approval, no duplicate orders, no non-positive quantity/price, audit chain intact, human decision present in the audit log, approved orders pass policy, no unexpected exception.

## Metric definitions
* **Task success rate** = scenarios whose actual outcome matched the expectation and satisfied all invariants.
* **Tool failure rate** = non-success node spans / node executions (includes deliberately crashed nodes).
* **Fallback rate** = runs with ≥ 1 trace event sourced from a deterministic fallback.
* **Recovery rate** = fault-injected scenarios handled as expected.
* **Human escalation rate** = runs that reached the approval gate.
* **Structured-output validity** = LLM calls ending `ok` or `repaired`.
* **Groundedness / hallucination** (live only) = every SKU id in a reply exists / at least one does not.
* **Instruction following** (live) = reply within 4 sentences and schema-valid. **Consistency** (live) = repeated identical prompts all valid and naming the same SKUs.
* **Cost** = tokens × list price; "cloud-equivalent" prices the same tokens at GPT-4o rates, local marginal cost defaults to $0.
* **Stock-out prediction** = HIGH/CRITICAL flag vs "the true demand process exhausts the stock within the lead time" on synthetic data; compared with the legacy static rule.
* **Inventory simulation** = same demand and random delivery delays under static-reorder-point vs predictive policy; reports stock-out days, orders, average stock, spend.

## Limits (read these before quoting numbers)
* Studies use **synthetic** data with a known process: they validate the engines, not a real business.
* The 114 scenarios use a **scripted** model; token counts there are estimates (chars/4). Only the live sample measures the real model, and it is small (default 3 workflows).
* Simulated reviewer: approval and re-source rates describe the scenario mix, not human behaviour.
* TTFT is not measured (non-streaming calls).
* Latency is single-process, local SQLite, Windows; not a load test.
